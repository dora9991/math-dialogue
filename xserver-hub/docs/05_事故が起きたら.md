# 05 事故が起きたら

「おかしい」と思ったら、**このページを上から**。完璧にやるより、早く止めて、記録を残すことが大事です。

以下、`hub` は `/usr/bin/php8.3 ~/hub/app/bin/hub` のこと。

## 最初の15分

1. **記録を始める**：紙かメモに、いまの時刻・気づいたこと・誰が気づいたか。以後、やったことを時刻つきで書き足す（下の「事故の記録」）
2. **止める**（迷ったら止める。止めても受信と台帳は動き続ける）

   | 何が起きていそうか | 止め方 |
   |---|---|
   | 送ってはいけないものが送られている | `hub line:stop` |
   | 管理画面に知らない人が入っているかも | `hub admin:logout-all` |
   | 何が起きているかわからない | `hub line:stop` と `hub maintenance:on`（管理画面と API も止まる。LINE の受信は続く） |

3. **消さない**：ログ・記録・あやしいファイルは、消したり直したりしない（調べる材料になる）。まず控える：
   ```bash
   hub backup                          # いまの DB（暗号化）
   hub audit:verify                    # 操作の記録が書き換えられていないか
   cp -a ~/hub/var/log ~/hub/var/log-incident-$(date +%Y%m%d-%H%M)
   ```
4. **一人で抱えない**：責任者（オーナー）へ連絡。夜でも

## 場面ごとの手順

### A. 管理画面のアカウントが乗っ取られたかも

（覚えのないログインの成功・知らない操作・「ログインの失敗が続いています」のメール）

1. `hub admin:logout-all`（全員をいますぐログアウト）
2. あやしいアカウントのパスワードと二段階認証を作り直す：
   ```bash
   hub admin:reset-password その人のメール
   hub admin:reset-2fa その人のメール
   ```
3. 何をされたかを調べる（管理画面「操作の記録」、または DB の `hub_audit_log`）：いつから・どの IP から・どの操作を
4. **何を見られたかを調べる**：閲覧の記録（`hub_access_log`）に、友だちの詳細・トークを開いた記録が残っています。誰の情報が見られたか＝報告の判断の材料
   ```sql
   SELECT at, actor_email, action, subject, ip FROM hub_access_log WHERE at >= '2026-10-01' ORDER BY at;
   ```
5. 一斉配信・設定の変更・運営メンバーの追加があれば、元に戻す（追加された運営メンバーは外す）
6. 原因をふさぐ：パスワードの使い回し・スマホの紛失・共用パソコン。必要なら `admin.allowed_ips` で管理画面の IP を絞る
7. 個人の情報が見られた・持ち出されたおそれがあれば → 下の「報告の判断」（**不正アクセスは、1人分でも報告の対象**）

### B. 秘密（config.php）が漏れたかも

（config.php を誤ってメール・チャット・git に貼った、サーバーに入られた、など）

秘密は全部入れ替えます。**DB の中身も漏れたかもしれない場合は、暗号化した中身も読まれたと考えます**（鍵と中身がそろうため）。

| 秘密 | 入れ替え方 |
|---|---|
| DB のパスワード | サーバーパネル「MySQL設定」でパスワード変更 → `config.php` の `db.pass` |
| LINE のチャネルシークレット | LINE Developers コンソール → チャネル基本設定 → チャネルシークレットの再発行 → `config.php` の `line.channel_secret` → `hub doctor --online`。長期のアクセストークンを使っていたら、それも再発行 |
| 会員サイトの API の秘密 | `hub keys:generate` → `config.php` の `member.api_keys.*.secret` と、会員サイト側の環境変数を同時に変える（古い鍵の名前を `disabled => true` にして、新しい名前の鍵を足すと、切り替えの間も止まらない） |
| 会員サイトへの知らせの秘密 | `member.webhook_secret` と、会員サイト側を同時に |
| Zoom の Secret Token | Zoom Marketplace で再発行 → `zoom.secret_token` |
| 暗号の鍵 | [04](04_日々の運用.md) の「鍵の入れ替え」。`keys.data` は k2 を足して `keys:rotate-data`。`keys.pepper` を変えたら全員 `admin:reset-password`。`keys.index` を変えたら、発行中の連携コード・回復コードが使えなくなる |
| 運営メンバーのログイン | `hub admin:logout-all` |

入れ替えたら `hub doctor --online`。

### C. 間違って送った（誤送信）

1. **`hub line:stop`**（まだ積まれている分を止める）
2. 管理画面「送信状況」：何を・何人に・いつ送ったか。まだ「待ち」の分が残っていないか
3. LINE のプッシュで送ったメッセージは、ハブからは取り消せません
4. 送った中身に **ほかの人の個人の情報** が入っていたら、それは漏えいです → 「報告の判断」
5. 必要なら、お詫びと訂正を送る（送る前に、絞り込みとテスト送信を確かめる）
6. 再発防止：一斉配信は、テスト送信と人数の確認をしてから。迷ったら練習モード

### D. 「LINE からの Webhook の署名が合いません」のメールが続く

- 誰かがハブの URL に偽の Webhook を送っています。ハブは断っているので、中身は入っていません
- チャネルシークレットを入れ替えた直後なら、`config.php` の写し間違い
- 心当たりがなく、ずっと続くなら、念のためチャネルシークレットを再発行（B の表）

### E. 「会員サイトの API に、署名の合わない呼び出しが続いています」のメール

- 鍵を入れ替えた直後でなければ、誰かが試しています
- API の秘密が漏れた心配があれば、B の表の「会員サイトの API の秘密」を入れ替える
- `member.api_keys.*.allow_ips` に、会員サイトのサーバーの IP を入れられるなら入れる（Supabase のように IP が決まらない場合は空のまま）

### F. 「操作の記録の鎖が切れています」

- 誰かが DB を直接書き換えた・行を消した可能性があります。**乗っ取りとして扱う**（A と B）
- `hub audit:verify` で、どこで切れたか。毎朝の報告メールに残っている「最新の指紋」と照らし合わせると、いつ以降が怪しいかがわかります

### G. データが消えた・サーバーが使えない

1. `hub backup:list` → `hub backup:verify <ファイル>` → `hub backup:restore <ファイル> --yes`（[04](04_日々の運用.md)「戻す」）
2. サーバーごと使えないとき：新しいサーバーに [02](02_Xserver初期設定.md) の手順で置き、`config.php`（鍵の控えから作り直す）を戻し、サーバーの外に持ち出したバックアップから戻す
3. 戻したあと、LINE の Webhook の再送で、止まっていた間のイベントが届きます（届かなかった分は、LINE からの「再送をやめました」のメールで期間がわかる）

### H. スマホ・パソコンを無くした

- 認証アプリのスマホ：回復コードでログインして、二段階認証を登録し直す。回復コードも無ければ、オーナーが `hub admin:reset-2fa`
- 管理画面にログインしたままのパソコン：`hub admin:logout-all その人のメール`
- SSH の鍵が入ったパソコン：サーバーパネル「SSH設定」で、その公開鍵を消す
- 個人の情報が入っていた（入れてはいけない決まりですが）なら → 「報告の判断」

## 報告の判断（個人情報保護委員会と、本人への通知）

個人データの漏えい・滅失・毀損（またはそのおそれ）が、次の **どれか1つ** に当たると、個人情報保護委員会への報告と、本人への通知が必要です（法26条、規則7条）。

1. **要配慮個人情報**（病歴など）が含まれる
2. 財産的な被害が生じるおそれがある（クレジットカード番号など）
3. **不正の目的をもって行われたおそれがある**（不正アクセス・乗っ取り・持ち出し。**人数にかかわらず**）
4. **1,000人を超える**

| | 期限 | 中身 |
|---|---|---|
| 速報 | 知ってから **速やかに**（目安：3〜5日以内） | その時点でわかっていること |
| 確報 | 知ってから **30日以内**（3. の場合は **60日以内**） | 原因・影響・再発防止まで全部 |

- 報告は、個人情報保護委員会の Web サイトの「漏えい等報告」のページから
- 当たらない場合も、何があって・どう判断したかを「事故の記録」に残す
- 判断に迷ったら、委員会の相談窓口に相談できます
- 期限や要件は改正されることがあるので、そのときに委員会の最新の情報で確かめてください

ハブの記録で答えられること：

| 知りたいこと | どこを見る |
|---|---|
| 誰の情報が見られたか | 閲覧の記録（`hub_access_log`） |
| 何が操作されたか | 操作の記録（管理画面「操作の記録」・`hub_audit_log`） |
| 何を・誰に送ったか | 送信状況（`line_outbox`。保存期間内） |
| いつ・どこから入られたか | 操作の記録の IP・`auth.login` の行 |
| DB が持ち出されたとき、何が読めるか | [07 データ台帳](07_データ台帳.md)（暗号化している列は、鍵が無ければ読めない） |
